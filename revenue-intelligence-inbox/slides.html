Interface choices & deliberate omissions

What I built

  • Dashboard with defined-denominator metrics, person/source-type filters, and drill-down to records
  • Conversation list with route badges, text coverage, and review state
  • Record detail with transcript, evidence-linked analysis, and route correction
  • Import/replay panel with step-by-step replay and M07 tracking
  • Manager brief for 21 Aug 2026 with evidence-linked priorities
  • Export with organised folders and JSON+CSV manifest
  • Metrics & definitions panel making every number auditable

What I deliberately left out

  • No pipeline value totals — no authoritative deal-value table exists; inventing one would mislead
  • No cross-person performance rankings — the sample is selected, not representative
  • No account matching — no verified company-ID join; similar titles aren't identity
  • No speaker talk ratios — phone text has no trustworthy turn timing; meeting speakers are local labels
  • No live AI — pre-generated analysis is honest about what's computed vs. prepared
  • No generic summaries — each of 18 conversations gets differentiated analysis
Design principle: every headline number has a defined denominator, a stated period, and a note on whether missing information affects it. The manager can drill from any number to the supporting source record.

Routing/folder design & one difficult case

7 routing categories

🎯 Sales Coaching (5)
💼 Deal Follow-up (7)
🤝 Customer Success (3)
🔗 Partnership (2)
🔍 Vendor Eval (1)
📋 Internal (1)
📥 Intake Required (26)

Manual overrides take precedence. The manager can change any route; corrections persist across updates and refreshes.

Folder structure

exports/ sales-coaching/ 5 files deal-followup/ 7 files customer-success/ 3 files partnership/ 2 files vendor-evaluation/ 1 file internal/ 1 file intake-required/ 26 files manager-brief.md manifest.json + .csv

Each record's analysis file lives in its route folder. If a route changes, the old file is superseded by the new one.

Difficult routing case: M07 (Willowfield Trust)

Initial state: No transcript (withheld for the update test) → routed to Intake Required. No fabricated analysis.

After update: 27 turns reveal a customer support session with 4 bugs — one urgent (payments stuck in Processing).

Decision: Route to Customer Success with analysis citing Turn 19 as the urgent evidence. If the manager manually set a route before the update, the manual route is preserved — the suggested route updates, but the override wins.

The difficulty: the conversation serves a single purpose (bug triage) but spans four issues with different urgencies. I chose one route (CS) with the analysis differentiating urgency internally, rather than splitting into four outputs. This keeps the export structure simple while the analysis communicates the priority hierarchy.

How I verified a key number & a key conclusion

Checking a key number: 44 unique records

Claim: 44 distinct (source_type, source_id) after applying revisions, not 45 (initial 44 + update 1).

How I checked:

  • Initial batch has 44 records, all revision 1 → 44 stored
  • Update batch has 1 record (M07), revision 2 → M07 is an existing key, so it replaces, not adds
  • Re-importing initial (revision 1) after update → M07's applied rev is 2, incoming is 1 → ignored as older
  • Result: 44 → 44 → 44 across all replay steps

Verified with a Node script replicating the import logic. The app shows this in the Import panel's record-count card and import log.

Checking a key conclusion: M03 price transparency

Claim: The rep conflated a recurring subscription (INR 26k) with a bundled setup charge (INR 13k), causing the customer to question the price increase.

How I traced it:

  • Turn 23: "But you previously told me INR 26,000. Why has that become INR 39,000?"
  • Turn 24: "I included the integration setup in that number. INR 26,000 is the recurring subscription, and INR 13,000 is the one-time setup."
  • Cross-check: 26,000 + 13,000 = 39,000 ✓ — the rep had quoted a bundled number without disclosing the split
  • Impact: next steps say "send itemised price breakdown — no bundled numbers"

The evidence is citeable by turn number in the app, and the analysis links both turns as supporting evidence with a "jump to turn" button.

Every metric in the dashboard links to its definition in the Metrics & Definitions panel. Every evidence item in the analysis links to the transcript passage. The manager can verify any number or conclusion by drilling from the overview to the source.

Trade-offs, AI usage & limitations

AI usage

  • Pre-generated analysis for all 18 text conversations — prepared by reading each transcript
  • Differentiated: no generic summaries; each analysis cites specific evidence
  • Manager brief pre-generated for 21 Aug 2026
  • Routing, metrics, import/dedup, export generation computed at runtime
  • No live AI calls; no API keys in the submission

Rejected decision

Considered: Runtime LLM analysis for each conversation.

Rejected because: API keys can't be in the submission; pre-generated analysis is explicitly allowed; runtime analysis would make the replay test non-deterministic.

Trade-off: When source text changes, the app shows a freshness indicator and marks review state — rather than silently regenerating. This is honest about limitations. The resulting choice: the analysis_fresh field in the manifest and the freshness indicator in Record Detail.

Known limitations

  • No CRM opportunity table or authoritative deal value — opportunity signals come from conversation evidence only
  • No cross-meeting speaker directory — speaker labels are local to each meeting
  • No talk ratios for calls — phone text has no trustworthy turn timing
  • localStorage persistence (~5MB) — sufficient for 44 records, not for scale
  • Pre-generated analysis covers 18 conversations; new text at runtime would route to intake
  • The data is de-identified and adapted — not a verbatim export

What I'd improve next

  • Server-side persistence (PostgreSQL) instead of localStorage
  • Optional LLM analysis with the user's own API key (clearly labelled)
  • Multi-route support (a conversation producing outputs for multiple destinations)
  • Full-text search across transcripts and analysis
  • Trend views across multiple days (the sample is a single date)
Approximate time spent: 7 hours. Built with React + TypeScript + Vite + Tailwind. All source files included. Export files generated from the app's Export panel.
